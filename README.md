# Mahan Panel — VLESS WS/XHTTP

پنل مدیریت کانفیگ‌های VLESS روی WebSocket/XHTTP، با موتور داخلی Node.js؛
این مسیرهای پیش‌فرض به xray-core نیاز ندارند. یک مسیر اختیاری و جداگانهٔ
VLESS/TCP + REALITY با Xray پین‌شده و خاموش به‌صورت پیش‌فرض نیز ارائه شده است.

> **مهم:** REALITY استفادهٔ VPN، پردازش و مقصدهای خروجی را از میزبان خودِ سرور
> پنهان نمی‌کند. پورت TCP خام، بررسی رسیدن IP واقعی کلاینت، cgroup و حداقل ۲۵۶ MiB
> لازم‌اند؛ فعال‌کردنش در ۱۲۸ MiB پشتیبانی نمی‌شود. اگر TCP proxy آدرس مبدأ را
> جایگزین کند، محدودیت دستگاه بر اساس IP قابل اتکا نیست. راه‌اندازی، هش باینری،
> محدودیت‌ها و تست‌ها: [راهنمای REALITY اختیاری](REALITY_OPTIONAL_GUIDE.md).
>
> **سیاست Railway:** مستندات [Trust and Safety](https://docs.railway.com/platform/trust-and-safety)
> و [قوانین استفاده](https://railway.com/legal/acceptable-use) اجرای VPN و پروکسی را
> ممنوع می‌کنند. امکانات فنی یا تغییر fingerprint به‌معنی مجاز بودن نیستند؛ برای
> این کاربرد، میزبانی را انتخاب کنید که صریحاً اجازهٔ VPN/پروکسی می‌دهد.

سازگار با **Abasthan** و **Deplexo** — دو پلتفرمی که رفتار مخالفی دارند:

| | Abasthan | Deplexo | Belmo (Coolify) |
|---|---|---|---|
| بیلد | محیط **تمیز**؛ Build Command باید وابستگیها را نصب کند | Dockerfile؛ `npm ci` داخل ایمیج | Dockerfile (توصیه) یا Nixpacks |
| استارت | `npm start` → `PORT` تزریق خودکار | CMD ایمیج `node server.js` | `node server.js` / `npm start` |
| فایل سیستم | قابلنوشتن | **فقطخواندنی** + volume پایدار `/data` | قابلنوشتن (موقت) |

**ماتریس Build Command — خیلی مهم:**

| پلتفرم | Build Command |
|---|---|
| Abasthan | `npm ci && npm run build` |
| **Belmo / Coolify (Nixpacks)** | خالی یا `npm run build` |
| **Belmo / Coolify (Dockerfile)** | خالی |
| Deplexo | خالی |

> ⚠️ هرگز `npm ci && npm run build`ـه Abasthan را روی Nixpacks/Coolify کپی نکنید؛
> Nixpacks خودش `npm ci` را در فاز install اجرا میکند و `npm ci` دوم با کش
> `/app/node_modules/.cache` برخورد میکند → `EBUSY` → بیلد fail.
> `nixpacks.toml` این پروژه جلویش را میگیرد.

برای همین `scripts/ensure-deps.js` وجود دارد: **فقط وقتی وابستگیها واقعاً کم باشند**
`npm ci` میکند. روی Deplexo یک no-op است و هیچ `npm install`ای در استارتاپ اجرا نمیشود
(جلوگیری از خطای `EROFS`)؛ روی Abasthan نصب میکند تا `Cannot find module 'express'`
و بهدنبالش `no_live_port` رخ ندهد.

## اجرای محلی

```bash
npm ci
npm start              # http://localhost:3000/  (admin / admin)
```

## بستهٔ اختیاری رمزگذاری‌شده

برای ساخت یک بستهٔ مستقل پیش از ارسال به میزبان، از `npm run package:protected`
و **[راهنمای بستهٔ رمزگذاری‌شده](PROTECTED_RELEASE_GUIDE.md)** استفاده کنید. این
گزینه مسیر عادی اجرای برنامه را تغییر نمی‌دهد. رمزگذاری فقط از فایل بسته در برابر
کسی که به کلید دسترسی ندارد محافظت می‌کند؛ میزبان هنگام اجرا به کلید و فایل‌های
رمزگشایی‌شده دسترسی دارد و ممکن است ماهیت برنامه را تشخیص دهد. مخزن اصلی فعلی
عمومی است؛ این روش کد منتشرشده یا تاریخچه و کپی‌های آن را پنهان نمی‌کند.

## پلن ۱۲۸ مگابایتی (کاهش خطر OOM و حفظ اتصال‌ها)

گارد حافظه مصرف cgroup را پایش می‌کند و همراه backpressure، بافرهای WS/XHTTP را
در فشار کم می‌کند و جریان TCP را موقتاً آهسته می‌کند. اتصال‌های برقرارشده برای
آزادکردن حافظه عمداً بسته نمی‌شوند، اما در بار مداوم ممکن است اتصال جدید بعد از
انتظار `503` بگیرد. OOM یا نبودِ قطعی در همهٔ شرایط قابل تضمین نیست.

برای یک سرویس ۱۲۸ MiB، در Environment داشبورد:

```text
MEMORY_LIMIT_MB=128
NODE_OPTIONS=--max-old-space-size=48 --max-semi-space-size=1
```

بعد از Redeploy، `GET /api/health` و فیلد `memory_guard` را بررسی کنید. در پلن‌های
بزرگ‌تر هم گارد به‌طور پیش‌فرض در ۶۲٪ وارد حالت `soft` و در ۷۸٪ وارد حالت `hard`
می‌شود؛ در حالت `hard` اتصال جدید ممکن است رد شود، حتی اگر هیچ اتصالی برقرار نباشد.
برای تشخیص، مقدار `rejected_new_connections` را پیش و پس از تلاش برای اتصال مقایسه کنید.

وقتی سقف حافظه مشخص باشد، عدد RAM داشبورد و گارد از یک مبنا استفاده می‌کنند.
مصرف cgroup شامل cache و حافظهٔ کرنل نیز هست و لزوماً فقط مصرف Node نیست؛ منبع
اندازه‌گیری در `ram_source` و `memory_guard.usage_source` گزارش می‌شود. fallback
از نوع `rss` فقط یک تخمین از مصرف پردازش است.

جزئیات، محدودیت‌ها و نتایج تست واقعی cgroup:
**[LOW_MEMORY_128MB_GUIDE.md](LOW_MEMORY_128MB_GUIDE.md)**. تست رگرسیون: `npm test`.

## پایداری اتصال و عیب‌یابی

- جریان TCP برقرار و سالم در WS/XHTTP/MUX صرفاً به‌خاطر سکوت بسته نمی‌شود و
  نشست سالم XHTTP هم صرفاً به‌خاطر بیش از هشت جریان هم‌گروه حذف نمی‌شود.
  تنظیم‌های قدیمی `XHTTP_MAX_CONNECTIONS_PER_COHORT` و `XHTTP_MIN_IDLE_BEFORE_TRIM_MS`
  فقط به پاک‌سازی رکوردهای بسته مربوط‌اند، نه سقف نشست‌های زنده. محدودیت کاربر و
  گارد حافظه همچنان اعمال می‌شوند.
- هدرهای تکه‌تکهٔ VLESS، MUX، و UDP با مقصدهای دوآدرسی یا فقط IPv6 پوشش داده
  شده‌اند (مقصد IPv6 به پشتیبانی شبکهٔ میزبان از IPv6 نیاز دارد). هر جریان UDP
  از یک آدرس DNS معتبر ثابت استفاده می‌کند؛ جریان‌های جدید همچنان می‌توانند به
  آدرس‌های دیگر بروند. محدودیت ثابت تعداد بسته حذف شده است، ولی صف محدود است و
  UDP همچنان ممکن است در ازدحام حذف شود. ترافیک دریافتی نیز تایمرهای idle مربوط
  به UDP و MUX را تازه می‌کند. متغیرهای قدیمی `BOOSTER_UDP_BURST_PACKETS` و
  `BOOSTER_UDP_BURST_WINDOW_MS` دیگر محدودیت تعداد بسته اعمال نمی‌کنند.
- در XHTTP packet-up، خوانندهٔ بدنه پس از خواندن POST آزاد می‌شود و منتظر DNS،
  اتصال یا نوشتن مقصدِ همان نشست نمی‌ماند؛ تعداد خواننده‌های هر نشست و کل منتظران
  نیز محدود است تا بدنه‌های ناقص یک نشست بقیه را متوقف نکنند. صف سقف تعداد و
  حجم دارد و در اشباع ممکن است POST با `503` رد شود. پیش‌فرض تعداد بسته‌های
  نامرتب هر نشست اکنون ۳۲ است؛ چندین نشست کند یا اشباع کامل همچنان می‌توانند
  باعث انتظار یا رد درخواست شوند.
- لینک‌های XHTTP جدید فاصلهٔ HTTP/2 PING را ۴۵ ثانیه می‌گذارند، نه ۲ ثانیه؛
  PING بسیار پرتکرار در بعضی پراکسی‌ها ممکن است رد شود، ولی معلوم نیست Railway
  یا Hostless چنین سیاستی داشته باشند. برای اعمال این تغییر روی کلاینت، اشتراک را
  به‌روزرسانی یا لینک ثابت XHTTP را دوباره وارد کنید. این PING تا Node نمی‌رسد
  و تضمین‌کنندهٔ بازماندن پاسخ HTTP یا جلوگیری از همهٔ قطعی‌ها نیست.
- گارد برای هر پذیرش حافظه را فوراً نمونه‌برداری می‌کند، ولی در فشار ثابت لازم
  نیست همهٔ اتصال‌های موجود را برای هر اتصال جدید دوباره پردازش کند. پردازش
  دوره‌ای و واکنش فوری به تغییر وضعیت فشار حفظ شده‌اند.
- TCP keepalive فعال است، اما WebSocket ping سرور فعال نشده است. تلاش اتصال
  ناقص، نشست XHTTP راه‌نیفتاده و UDP بیکار همچنان timeout دارند؛ قطع مقصد/شبکه،
  محدودیت quota، reverse proxy و ریست/OOM نیز می‌توانند اتصال را ببندند. نگه‌داشتن
  جریان‌های بیکار منابع مصرف می‌کند و گارد ممکن است اتصال‌های جدید را رد کند؛
  تشخیص اتصال نیمه‌باز هم فوری نیست. قطعی صفر قابل تضمین نیست.

پس از واردکردن تغییرات در نسخهٔ دیپلوی‌شده، **Redeploy** کنید و در
`GET /api/health` مطمئن شوید `build` برابر `optional-reality-r1` است.
اگر مشکل ادامه داشت، نوع WS/XHTTP/MUX، نام کلاینت، فاصلهٔ تقریبی تا قطع، روش
اندازه‌گیری پینگ و لاگ همان لحظه را بررسی کنید. پیش از ارسال لاگ، UUID، توکن،
آدرس IP و مقصدها را حذف کنید. وضعیت و شمارنده‌ها مربوط به عمر فعلی پردازش هستند
و بعد از ریست صفر می‌شوند؛ دو snapshot به‌تنهایی علت همهٔ قطعی‌ها را ثابت نمی‌کنند.

در `/api/health`، فیلد `transports` شمارندهٔ کلی باز/بسته‌شدن WS و sessionهای
XHTTP، دستهٔ تقریبی بسته‌شدن و تعداد خطاهای `503`/`413` برای packet POST را نشان
می‌دهد. `peer` می‌تواند بستن طبیعی کلاینت **یا** قطع پراکسی/شبکه باشد؛ اینها تعداد
کاربران یا قطعی‌های قطعی نیستند. `memory_guard.xhttp_packet_buffer_*` حجم/تعداد صف
و سقف پایهٔ آن را نشان می‌دهد؛ برای رفع بن‌بست، یک بستهٔ موردانتظار اضافی تا سقف
یک POST مجاز است. `pending_xhttp_requests` درخواست‌های منتظر پذیرش حافظه را
می‌شمارد. همهٔ این شمارنده‌ها تجمیعی و بدون شناسهٔ کاربر/مقصد هستند و با ریست صفر
می‌شوند. `event_loop_delay.current` و `previous` نمونه‌های پنجرهٔ ۱۰ ثانیه‌ای با
دقت ۲۰ میلی‌ثانیه هستند و فشار CPU/GC را بهتر نشان می‌دهند، **نه پینگ شبکه**.

فیلد `udp_drops` در `/api/health` فقط حذف‌های داخلی برنامه را می‌شمارد:
`uplink_queue_full` یعنی صف محدود ارسال به مقصد پر شده و `downlink_pressure`
یعنی گیرندهٔ WS/XHTTP به‌اندازهٔ کافی سریع نمی‌خوانَد. افزایش شمارنده‌ها را پیش
و پس از بروز مشکل مقایسه کنید. صفر بودن آنها سلامت شبکه، حذف‌نشدن بسته در سیستم‌عامل
یا اینترنت، و پایداری پینگ TCP را ثابت نمی‌کند. حتی در فشار واقعی هم ممکن است UDP
حذف شود تا مصرف حافظه نامحدود نشود.

اگر `storage` برابر `ephemeral-tmp` است، دیتابیس `/tmp` پس از ریست/دیپلوی ممکن
است پاک شود؛ برای ماندگاری از volume پایدار و `DB_PATH` مناسب استفاده کنید.

### ترافیک زمان بیکاری و اطلاعات آشکار

- خودپینگ برنامه، مگر با `KEEPALIVE_ENABLED=0`، به‌طور پیش‌فرض هر چهار دقیقه
  فعال است **اگر URL معلوم باشد**. URL تنظیم‌شده در `KEEPALIVE_URL` اولویت دارد؛
  در غیر این صورت به‌صورت پیش‌فرض از `Host` درخواست‌های ورودی استخراج می‌شود و
  می‌تواند loopback یا اطلاعات ارسالیِ نامطمئن باشد. وضعیت، URL تنظیم‌شده یا
  کشف‌شده، منبع، تعداد تلاش‌ها، درخواست‌های در جریان و آخرین خطا را پس از ورود
  مدیر در `GET /api/keepalive` ببینید؛ برای URL صریح، برنامه `/health` را به
  انتهای URL پایه اضافه می‌کند و redirect نیز ممکن است هدف نهایی را تغییر دهد.
  پیش از اشتراک‌گذاری، URL و اطلاعات حساس را حذف کنید.
  مقدار نامعتبر `KEEPALIVE_INTERVAL_MS` به چهار دقیقه برمی‌گردد؛ مقدار خیلی کوچک
  حداقل ۶۰ ثانیه و مقدار بزرگ حداکثر `2147483647` میلی‌ثانیه می‌شود، تا تبدیل
  تایمر معیوب Node به فاصلهٔ ۱ میلی‌ثانیه باعث سیل درخواست نشود.
- برای جلوگیری از انتخاب هدف از هدر نامطمئن، `KEEPALIVE_AUTO_DETECT=0` بگذارید و
  اگر خودپینگ لازم است `KEEPALIVE_URL` را صریحاً تنظیم کنید. بدون URL صریح در این
  حالت، خودپینگ ارسال نمی‌شود. `KEEPALIVE_USER_AGENT` فقط هدر همان خودپینگ را
  تغییر می‌دهد؛ پیش‌فرض برای سازگاری تغییر نکرده و ممکن است WAF به آن وابسته باشد.
- در **Settings → System → Optional self-ping**، مدیر می‌تواند خودپینگ را موقتاً
  متوقف/ادامه کند؛ درخواست‌های خودپینگ در جریان نیز هنگام توقف لغو می‌شوند.
  این کار به سوکت‌های کاربران دست نمی‌زند، ولی ممکن است میزبان سرویس بیکار را به
  خواب ببرد. مثلاً [پلن Free Railway](https://docs.railway.com/pricing/free-plan)
  در شرایط بی‌فعالیتی خروجی می‌تواند سرویس را بخواباند. تغییر موقت فقط برای همان
  پردازش/replica است و پس از ریست به مقدار محیط برمی‌گردد؛ در چند replica ممکن است
  درخواست‌های پنل به پردازش‌های متفاوت برسند. خاموش‌کردن خودپینگ به‌معنی حذف تمام
  فعالیت شبکهٔ میزبان، مانیتورینگ خارجی یا fallback اختیاری REALITY نیست و علت
  محدودیت را ثابت نمی‌کند.
- لاگ‌های عادی دیگر اتصال موفق را همراه مقصد/نام کاربر/دستگاه ثبت نمی‌کنند و
  UUID کاربران در لاگ ساخت/ویرایش چاپ نمی‌شود. `LOG_SENSITIVE_DETAILS=1` بخشی از
  جزئیات اتصال و خطا را برای عیب‌یابی بازمی‌گرداند؛ `DEBUG_ACTIVE_CLIENTS=1` هم
  ممکن است اطلاعات حساس چاپ کند. این کاهش جزئیات، پاک‌سازی جامعِ همهٔ خطاها،
  استثناها، لاگ‌های میزبان یا داده‌های موجود در دیسک و حافظه نیست.
- با `PUBLIC_HEALTH_MINIMAL=1` پاسخ ناشناس `/health` و `/healthz` فقط `ok` و پاسخ
  ناشناس `/api/health` فقط `{ "ok": true }` می‌شود؛ مدیرِ واردشده همچنان جزئیات
  کامل API را می‌بیند. پیش‌فرض برای حفظ سازگاری مانیتورینگِ فعلی تغییر نکرده است.
  این گزینه اطلاعات همهٔ صفحه‌ها، مسیرها، کد، پردازش یا ترافیک را مخفی نمی‌کند و
  ممکن است مانیتورینگ ناشناسِ وابسته به فیلدهای قبلی را نیازمند تغییر کند.

هیچ padding، تأخیر تصادفی یا تغییر پروتکلی به ترافیک کاربران اضافه نشده است؛
سازگاری و عملکرد محیط واقعی همچنان نیازمند تست‌اند. تنظیم متغیرهای محیط به دیپلوی
یا ریست نیاز دارد و **خودِ دیپلوی می‌تواند ارتباط‌های برقرار را قطع کند**. میزبان
همچنان پردازش، تنظیمات و جریان‌های شبکه را می‌بیند؛ این گزینه‌ها نه تشخیص‌ناپذیری
را تضمین می‌کنند و نه باعث مجاز شدن کاربرد ممنوع می‌شوند.

### نکتهٔ Railway برای XHTTP

> Railway اجرای VPN/پروکسی را ممنوع می‌کند. توضیح‌های فنی زیر مجوز استفاده نیستند.

- نشست XHTTP و سوکت مقصد در حافظهٔ همان پردازش هستند؛ GET و POST یک نشست باید به
  همان replica برسند. این محدودیت برای هر میزبان چند-replica صادق است. Railway
  درخواست‌ها را بین replicaها توزیع می‌کند و
  [sticky session ارائه نمی‌دهد](https://docs.railway.com/deployments/optimize-performance#load-balancing-between-replicas).
- طبق [محدودیت‌های رسمی شبکهٔ Railway](https://docs.railway.com/networking/public-networking/specs-and-limits)،
  درخواست HTTP در صورت انتقال داده حداکثر ۱۵ دقیقه و بدون انتقال داده ۵ دقیقه باز
  می‌ماند و آپلود بدنه باید ظرف ۵ دقیقه تمام شود. WebSocket از این محدودیت‌های
  خاص مستثناست؛ این معافیت ممنوعیت VPN/پروکسی را لغو نمی‌کند و جلوی قطع توسط
  کلاینت، شبکه، پراکسی‌های دیگر یا redeploy را نمی‌گیرد.
- اگر قبلاً تنظیمات پلن ۱۲۸ MiB را گذاشته‌اید و اکنون سرویس ۱ GiB است، بررسی
  کنید `MEMORY_LIMIT_MB=128` یا گزینه‌های `--max-old-space-size=48` و
  `--max-semi-space-size=1` در `NODE_OPTIONS` ناخواسته باقی نمانده باشند. سقف
  heap واقعی Node در `node_heap.limit_mb` در `/api/health` نمایش داده می‌شود؛
  با آن دو گزینه در این محیط حدود ۵۱ MiB است، مستقل از RAM کانتینر. فقط مقادیر
  نامناسب را مطابق پلن حذف یا تنظیم کنید، نه بقیهٔ گزینه‌های لازم برنامه را.
- پینگ می‌تواند به مسیر اینترنت، فاصله تا region، CPU، مقصد و نوع تست نیز وابسته
  باشد؛ حافظهٔ بیشتر به‌تنهایی پینگ ثابت یا اتصال بدون قطعی را تضمین نمی‌کند.

اگر پس از ۳۰–۶۰ دقیقه مشکلی رخ می‌دهد، ابتدا متن دقیق پیام و وضعیت workspace و
سرویس، پلن، زمان‌های رخداد و لاگ همان بازه را بررسی کنید: خواب سرویس، ریست/OOM،
پایان اعتبار، قطع اتصال و محدودیت workspace یکسان نیستند. مشاهدهٔ بدون کلاینت
الگوی ترافیک کلاینت را به‌تنهایی توضیح نمی‌دهد؛ نه خودپینگ و نه الگوریتم تشخیص
Railway بدون شواهد علت ثابت‌شده‌اند. برای محدودیت حساب، با پشتیبانی میزبان تماس
بگیرید؛ پیش از ارسال گزارش، UUID، توکن، IP، دامنه و مقصدها را حذف کنید. اگر
Workspace واقعاً restricted شده، خواب سرویس با آن متفاوت است و توقف/تغییر خودپینگ
به‌تنهایی رفع محدودیت حساب را تضمین نمی‌کند؛ دلیل و گزینهٔ اعتراض را در
[صفحهٔ محدودیت‌ها](https://railway.com/workspace/restrictions) بررسی کنید.

### Hostless Cloud و چند replica

همان محدودیت مالکیت session برای همهٔ میزبان‌ها صادق است: اگر Hostless چند replica
یا region دارد، GET و POST یک session باید به یک پردازش برسند؛ در نبود مسیریابی
session-aware، از یک replica/region استفاده کنید. تنظیمات واقعی سرویس شما مشخص
نیست؛ تعداد replica و سهم/محدودیت CPU را در تنظیمات همان سرویس بررسی کنید. مطابق
[مستندات Hostless](https://docs.hostless.cloud/app/scalingconfig)، درخواست و سقف
CPU جداگانه تنظیم می‌شوند؛ سقف CPU لزوماً سهم رزروشده نیست. زمان‌بندی قطع WS در
Hostless از این اطلاعات مشخص نمی‌شود.

### تست‌های تکمیلی محلی

`npm test` رگرسیون‌های خودکار را اجرا می‌کند. برای تست اختیاری با Xray-core واقعی
و OpenSSL، یک باینری سازگار جداگانه نصب کنید (این پروژه خود Xray را توزیع نمی‌کند؛
نسخهٔ آزمایش‌شده [Xray-core 26.3.27](https://github.com/XTLS/Xray-core/releases/tag/v26.3.27) بود):

```bash
XRAY_BIN=/path/to/xray XRAY_TEST_MEMORY_MB=128 XRAY_TEST_SOAK_SECONDS=30 npm run test:xray
```

این تست TLS/H2/H1، WS، packet-up و stream-up، MUX، UDP، مقصد کند، گیرندهٔ متوقف،
قطع شبیه‌سازی‌شده، تأخیر ساختگی و جریان‌های طولانی‌تر را در loopback آزمایش
می‌کند. `XRAY_TEST_MEMORY_MB` فقط آستانه‌های برنامه را شبیه‌سازی و در این تست
گارد را غیرفعال می‌کند؛ محدودیت واقعی حافظه نیست. تست جداگانهٔ
`npm run test:cgroup:xhttp` گارد فعال را با cgroup v2 واقعی، ۱۲۸ MiB، swap صفر و
سقف ۰٫۵ CPU می‌آزماید. این تست به Linux، `sudo` بدون رمز، `runuser` و Python نیاز
دارد و **نباید روی production اجرا شود**. هیچ‌کدام جایگزین آزمایش شبکه و لاگ
دیپلوی واقعی نیستند.
